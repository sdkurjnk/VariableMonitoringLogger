# 호출 컨텍스트 트리

각 이벤트가 "어느 호출에서 일어났는가"를 표현하는 방식과, 트리를 온전히 유지하기 위한 처리를 정리한다.

관련 코드: `CallContextManager`

---

## 무엇을 위한 것인가

변경 이력만으로는 부족한 경우가 있다. 재귀 함수나 반복 호출에서는 같은 줄, 같은 변수의 변경이 여러 번 찍히는데, 그것들이 **같은 호출 안에서 일어난 일인지 서로 다른 호출인지** 구별되지 않으면 이력을 읽을 수 없다.

각 레코드에 붙는 세 필드가 이 문제를 해결한다.

| 필드 | 의미 |
|---|---|
| `call_id` | 호출 인스턴스의 고유 ID |
| `parent_call_id` | 호출한 쪽의 `call_id` (루트면 `null`) |
| `call_depth` | 루트로부터의 깊이 (루트가 1) |

`parent_call_id`로 부모를 따라가면 호출 트리가 복원된다.

## ID 공간을 공유하는 이유

`CallContextManager.next_id()`는 `call_id`와 **합성 identity**가 같은 카운터를 쓴다.

프레임 기반 `call_id`와, 클로저 셀에 부여되는 ENCLOSING `var_id`가 서로 다른 카운터를 썼다면 같은 숫자가 양쪽에서 나올 수 있다. 하나의 ID 공간을 공유하면 그런 충돌이 구조적으로 불가능해진다. 카운터 하나를 아끼는 것보다 ID의 전역 유일성을 얻는 쪽이 이득이라는 판단이다.

## gap 프레임 채우기

핵심 처리다. `ensure_context(frame)`는 컨텍스트가 없는 프레임을 만나면 `f_back`을 타고 **이미 컨텍스트를 가진 조상**을 찾을 때까지 거슬러 올라간 뒤, 그 사이의 프레임들에도 컨텍스트를 만들어 준다.

이유는 트리의 연결성이다. 로깅에 관련된 프레임만 컨텍스트를 갖는다면, 중간에 관련 없는 프레임이 끼었을 때 부모 연결이 끊기고 `call_depth`가 실제 호출 깊이와 어긋난다.

```
<module>        컨텍스트 있음
  └─ helper()   추적 변수와 무관 → 그냥 두면 컨텍스트 없음
       └─ work()  추적 변수 변경 발생
```

`helper`를 건너뛰면 `work`의 부모가 `<module>`이 되어 깊이가 하나 줄어든다. 중간 프레임을 채워야 트리가 실제 호출 구조와 일치한다.

## 로깅 조상이 없을 때

`f_back`을 끝까지 따라갔는데 컨텍스트를 가진 조상이 하나도 없으면, **요청된 프레임 자신이 새 체인의 루트가 된다.**

체인 끝까지 컨텍스트를 만들며 올라가지 않는 것이 의도적인 선택이다. 그렇게 하면 인터프리터 부트스트랩 프레임, `importlib` 내부, 테스트 러너 프레임 같은 **무관한 프레임들이 트리에 끌려 들어온다.** 사용자가 보고 싶은 것은 자기 코드의 호출 구조이므로, 트리의 뿌리를 사용자 코드 쪽에 두는 편이 유용하다.

대가로 `call_depth`는 인터프리터 시작점 기준의 절대 깊이가 아니라 **추적이 시작된 지점 기준의 상대 깊이**가 된다.

## gap 프레임 전용 정리 트레이서

컨텍스트를 만들었으면 프레임이 반환될 때 지워야 한다. 그렇지 않으면 프레임 객체를 키로 하는 `_contexts`가 계속 자란다.

관련 프레임은 자기 로컬 트레이서의 `return` 경로에서 `on_return()`을 부르므로 문제가 없다. 하지만 gap을 메우려고 자동 생성한 프레임에는 트레이서가 없다. 그래서 `_attach_return_cleanup()`이 가벼운 정리 전용 트레이서를 붙인다.

두 가지 배려가 들어가 있다.

**기존 트레이서를 덮어쓰지 않는다.** `f_trace`가 이미 있는 프레임은 관련 프레임으로 간주하고 손대지 않는다. 덮어쓰면 그 프레임의 변수 추적이 통째로 죽는다.

```python
previous_trace = getattr(frame, "f_trace", None)
if previous_trace is not None:
    return
```

**라인 이벤트를 끈다.** `f_trace_lines = False`로 두어 `return`만 받는다. gap 프레임은 변수를 볼 필요가 없으므로 라인마다 콜백을 받을 이유가 없다.

정리 시에는 `_restore_cleanup_trace()`가 원래 `f_trace`와 `f_trace_lines`를 되돌린다. 되돌리기 전에 현재 `f_trace`가 자신이 설치한 그 트레이서인지 확인하는데, 그 사이 다른 주체가 트레이서를 교체했을 수 있기 때문이다.

## 알려진 문제: 제너레이터 resume

CPython은 제너레이터가 resume될 때마다 "call" 이벤트를 재발생시킨다. 그 결과 **같은 제너레이터 프레임이 resume마다 새 `call_id`를 받아** 논리적으로 하나인 호출이 여러 개로 쪼개진다.

프레임을 키로 컨텍스트를 관리하는 현재 구조와 CPython의 이벤트 모델이 어긋나는 지점이다.
