# 프레임 부착 전략

`TraceDispatcher`가 어떤 프레임에 라인 트레이싱을 걸지 결정하는 방식과, 그 선택에 따르는 대가를 정리한다.

관련 코드: `TraceDispatcher._trace_calls`, `_ensure_frame_tracking`, `_make_line_tracer`, `register`

---

## 전역 훅을 "call" 이벤트로 좁힌 이유

`sys.settrace`에 등록된 `_trace_calls`는 `event != "call"`이면 즉시 `None`을 반환한다. 전역 훅의 역할을 **"이 새 프레임에 라인 트레이싱을 걸 것인가"** 하는 판단 하나로 한정한 것이다.

이렇게 좁힌 이유는 비용 때문이다. 전역 훅에서 라인 이벤트까지 받으면 추적 대상과 무관한 모든 코드가 매 줄 파이썬 콜백을 거치게 된다. 대신 `_relevant_for()`가 `f_code`와 `f_globals` 동일성으로 관련 여부를 판정하고, 관련 없는 프레임에는 아예 로컬 트레이서를 붙이지 않는다. 부착되지 않은 프레임은 이후 실행에서 완전히 제로 코스트다.

즉 **"관심 있는 프레임만 골라 라인 단위로 본다"** 가 성능 설계의 핵심이며, 프레임 선별이 그 전제다.

## 대가: 이미 실행 중이던 프레임

"call" 이벤트에만 반응한다는 것은, **훅 설치 시점에 이미 스택에서 실행 중이던 프레임은 영원히 잡히지 않는다**는 뜻이다. 그 프레임들은 앞으로 "call"을 다시 발생시키지 않기 때문이다.

이것은 `sys.settrace`의 성질이지 우회 가능한 구현 실수가 아니다. 그래서 `register()`가 **수동 부착 경로**를 함께 갖는다.

```python
# 등록 frame의 "call" 이벤트는 이 tracker가 생기기 전에 이미 발생했으므로,
# line tracing을 여기서 명시적으로 붙여야 한다.
frame_state = self._ensure_frame_tracking(frame)
```

`register()`에 넘어오는 `frame`은 `sys._getframe(1)`로 잡은 직접 호출자다.

## 두 가지 등록 경로

| 경로 | 대상 | 시점 |
|---|---|---|
| `_trace_calls` (자동) | register 이후 새로 생성되는 프레임 | "call" 이벤트 발생 시 |
| `register()` (수동) | 이미 실행 중이던 프레임 | register 실행 중 |

따라서 추적 가능 여부의 기준은 **스택상의 위치가 아니라 `sys.settrace` 호출 시점 대비 프레임의 생성 시점**이다. 같은 모듈의 형제 함수라도 register 이후에 호출되면 잡히고, 조상 프레임이라도 register 이전부터 실행 중이면 수동 부착 없이는 잡히지 않는다.

수동 부착의 범위는 `frame.f_back` 체인 전체가 되어야 한다. 그 체인이 곧 "register 시점에 이미 실행 중인 프레임"의 집합이기 때문이다.

## 라인 트레이서를 프레임마다 새로 만드는 이유

`_trace_calls`는 단일 메서드를 반환하지 않는다. `_ensure_frame_tracking`이 `_make_line_tracer(frame_state)`로 만든 **프레임 전용 클로저**를 `f_trace`에 붙이고, 그 값을 반환한다.

클로저를 쓰는 이유는 각 트레이서가 자기 프레임 전용 `frame_state` 딕셔너리를 캡처해야 하기 때문이다. 같은 코드 객체가 여러 프레임에서 동시에 살아 있는 상황(재귀 호출이 대표적)에서 각 호출이 독립된 변수 상태를 갖도록 보장한다. 코드 객체를 키로 상태를 공유했다면 재귀 호출들이 서로의 이전 값을 덮어썼을 것이다.

## 정리 시점

로컬 트레이서는 매번 자기 자신을 반환해 다음 라인에서도 호출되게 하고, `return` 이벤트에서 `None`을 반환해 스스로를 떼어낸다. 이때 `_frame_states`와 `_frame_cell_cache`에서 해당 프레임 항목을 제거한다.

프레임 객체를 키로 쓰는 자료구조들이므로, 이 정리가 빠지면 상태가 프레임보다 오래 살아남아 누수가 된다.

## 제너레이터와 코루틴

suspend된 제너레이터 프레임은 `f_back` 체인에 존재하지 않는다. 스택에 올라와 있지 않기 때문이다.

다만 CPython은 제너레이터가 resume될 때마다 "call" 이벤트를 다시 발생시키므로 자동 경로로 처리된다. 부작용으로 resume마다 호출 컨텍스트가 재생성되는 문제가 있다(→ [호출 컨텍스트 트리](./call-context.md)).
