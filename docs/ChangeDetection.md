# 변경 감지 전략

매 라인마다 "이 변수가 바뀌었는가"를 판정하는 방식과, 비용을 낮추기 위한 단계적 설계를 정리한다.

관련 코드: `VariableTracker.check`, `_make_state`, `oscilo_engine.c`

---

## 전제: 라인마다 실행되는 코드다

이 판정은 추적 대상 프레임의 **모든 실행 줄마다** 돈다. 따라서 판정 로직의 비용이 곧 도구 전체의 오버헤드가 된다.

설계의 뼈대는 하나다 — **싼 검사부터 시도해서, 비싼 검사에 도달하기 전에 최대한 결론을 내린다.** 아래 사다리는 비용 순으로 배열되어 있고, 각 단계는 "이 검사만으로 확정할 수 있는가"를 기준으로 나뉜다.

## 단축 평가 사다리

```
1. 참조 동일성이 바뀌었는가?        → 바뀜 (재할당 확정)
2. 불변 타입인가?                   → 안 바뀜 (제자리 변경 불가)
3. 컨테이너 크기가 달라졌는가?      → 바뀜 (전체 비교 불필요)
4. 값을 비교한다                    → 바뀜 / 안 바뀜
```

각 단계의 근거:

**1. 참조 동일성** — 포인터 비교 한 번이다. 다르면 재할당이 있었다는 뜻이므로 값을 볼 필요 없이 확정된다.

**2. 불변 타입 조기 탈출** — `int`, `str`, `float`, `bool`, `None`은 참조가 그대로라면 제자리 변경이 불가능하다. 값 비교를 아예 건너뛴다. 실제 코드에서 가장 흔한 타입들이라 이 분기가 걸러내는 비율이 높다.

**3. 크기 비교** — 리스트·딕트·셋·튜플은 길이만 봐도 변경을 증명할 수 있다. O(1) 검사로 O(n) 비교를 피한다. 단 크기가 같다고 값이 같은 것은 아니므로 여기서 "안 바뀜"을 확정하지는 못하고 다음 단계로 넘어간다.

**4. 값 비교** — `PyObject_RichCompareBool`로 전체 비교. 여기까지 온 경우에만 O(n) 비용을 지불한다.

## 파이썬 쪽 사전 분기

C 호출 자체도 공짜가 아니므로, `VariableTracker.check`가 그 앞에서 한 번 더 거른다.

원자 타입(`int`, `float`, `bool`, `complex`, `str`, `bytes`, `None`)은 `_make_state`에서 스냅샷을 만들지 않는다. 이때 `state["copy"]`가 `None`이라는 사실 자체가 "원자 타입"의 표식이 되고, 참조 비교만으로 판정이 끝나 C 확장을 호출하지 않는다.

## C 확장으로 뺀 이유

위 사다리는 매 줄 실행된다. 파이썬으로 작성하면 판정 로직 자체의 인터프리터 오버헤드가 추적 대상 코드보다 커질 수 있다.

`oscilo_engine`은 이 판정만 담당하는 작은 확장 모듈이다. 스코프 딕셔너리 조회, 참조 비교, 타입 검사, 크기 비교를 C 레벨에서 수행한다. 스냅샷 생성(`deepcopy`)과 이벤트 기록은 파이썬 쪽에 남겨, C 코드가 다뤄야 할 상태를 최소화했다.

## 스냅샷: 왜 튜플도 깊은 복사인가

원자 타입이 아닌 값은 `copy.deepcopy`로 분리된 스냅샷을 만든다. 튜플처럼 **불변 컨테이너도 예외가 아니다.**

튜플 자체는 재할당될 수 없지만 가변 객체를 담을 수 있기 때문이다. `t = ([1], [2])`에서 `t[0].append(3)`은 튜플의 참조도 크기도 바꾸지 않지만 값은 바뀐다. 얕은 복사로는 원본과 스냅샷이 같은 리스트를 가리켜 변경을 놓친다.

이 결정의 대가는 명확하다 — 초기화와 변경 시마다 깊은 복사 비용이 든다. 큰 자료구조를 추적하면 여기가 가장 비싼 지점이다. 다만 이 비용은 **변경이 감지된 순간에만** 발생하고, 변경 없는 줄에서는 사다리 1~3단계에서 끝난다.

## 스냅샷을 외부에 그대로 주지 않는 이유

`get_snapshot()`은 저장된 스냅샷을 다시 깊은 복사해서 돌려준다. 호출자가 반환값을 변형하면 내부 기준값이 오염되어 이후 비교가 전부 틀어지기 때문이다.

같은 이유로 `HistoryBuffer.getHistory()`도 깊은 복사를 반환한다.

## Python 3.13+ 대응

3.13부터 `frame.f_locals`가 프록시 객체로 노출될 수 있다. C 코드는 버전에 따라 조회 방식을 나눈다.

- 3.13 이상: `PyObject_GetItem` (프록시를 통과)
- 그 미만: `PyDict_GetItem` (borrowed reference이므로 `Py_XINCREF` 필요)

## 이벤트 분류

판정 결과는 다섯 가지로 나뉜다.

| 이벤트 | 조건 |
|---|---|
| `init` | 이전 상태가 없음 (첫 관측) |
| `updated` | 참조 또는 값이 변경됨 |
| `no_change` | 변경 없음 — 기록하지 않음 |
| `deleted` | 스코프에서 사라짐 (이전 상태가 있었음) |
| `not_found` | 스코프에 없음 (이전 상태도 없었음) |

`no_change`가 레코드를 남기지 않는 것이 출력 크기를 억제하는 핵심이다. 대부분의 줄은 추적 변수를 건드리지 않으므로, 실행 줄 수가 아니라 실제 변경 횟수에 비례해 로그가 자란다.
